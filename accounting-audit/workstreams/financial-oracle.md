# Financial oracle workstream

Audit only. Two confirmed current-logic findings: **F-001 High** (return before source changes earlier financial reports) and **F-002 Critical** (consumed store credit can be voided/reissued/spent twice). Production code and existing tests were not edited. All dynamic transactions ran through authenticated mounted Express routes against new disposable databases; no legacy/customer database was opened.

## Safety and oracle

`accounting-audit/tests/oracle-lifecycle.cjs` creates a unique `accounting-audit/evidence/oracle-run-*` directory before importing backend code, sets NODE_ENV=test and DATABASE_PATH, and wraps better-sqlite3 construction to reject every path outside that directory. The actual schema/migrations and seeded administrator are loaded, then real cookie login and supertest requests drive the mounted app. Database/schema/API/SQL evidence is retained. `database-proof.json` extractions open only known audit DB paths in readonly mode and verify integrity/FKs.

Independent expectations are derived from fixture input using integer paise (BigInt parser/multiplication for retail, integer constants for remaining monetary scenarios), never copied from the observed financial outputs. SQL checkpoints also execute all exported A–J and additional credit-source/unapplied-liability, supplier-advance, expense-payable and input-tax collectors. Each journal_entry_id balances independently, preventing aggregate reference groups from hiding offsetting journal defects. Supplemental runs additionally compare signed GL1100+1110 against signed customer net balances. Rejected mutations capture before/after SHA-256 economic-state hashes. No economic behavior is mocked; only the standalone Jest assertion import is adapted so existing SQL collectors can run outside Jest.

All date strings are explicit except operations whose supported API uses system date (damage transfer/write-off and return settlements). Retail reports intentionally include September1 through October31 to capture the October25 write-off/refunds. Invoice-return-spec.md D14 explicitly chooses document/GL date versus today's customer-ledger date; this known hybrid is not reported as a new defect.

## Remaining limits

This is risk-based evidence, not proof of all financial workflows. Carton-to-unit conversion was not exercised: graph query returned no matching conversion symbol and literal searches found no carton/pack conversion surface; inspected Item and purchase DTOs carry a unit label and quantity rather than a discovered conversion ratio. This is a coverage gap, not an invented product defect. Payroll, loans, production, owner-equity edge cases and expense-payable recognition are covered by the backend-controls owner. Full server/Flutter suites and quick/static checks are leader-owned and intentionally not duplicated here. No historical dummy-data repairs or re-audits occurred.
