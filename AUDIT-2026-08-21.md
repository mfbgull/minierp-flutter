## READ THIS FIRST — three framing facts

**1. The database was live and changing throughout this audit.**
All figures below are as-at a read-only snapshot taken **2026-08-21 23:34 PKT** (`erp.db` last written 03:53, WAL last written 23:09). Between the first and last snapshot of this audit, `customers` went 11 → 1, `items` 13 → 10, `purchases` 1 → 0, `stock_batches` 5 → 4. The Rupee amounts in this report are therefore evidence *at an instant*, not constants. **The structural findings are stable; the numbers are not.** Where an earlier figure differs from one quoted here, this document's number is the later and authoritative one.

**2. There is a dated failure that fires on 2026-09-01 — ten days from now.**
`accounting_periods` contains exactly one row: `2026-08` / `2026-08-01` → `2026-08-31` / `open`. `AccountingService.postEntry` (`server/src/services/accountingService.ts:225-238`) throws when no open period covers the entry date, and it is called *inside* `Invoice.create`'s transaction. On 1 September, **creating an invoice will fail outright** with `No open accounting period covers 2026-09-01`. This is a ~10-line fix and it is the most time-critical item in this report. See **ACC-11 / #2** below.

**3. There is no backup. Not a weak backup — none.**
Zero occurrences of `VACUUM INTO`, `.backup(`, `sqlite3_backup` or `PRAGMA integrity_check` anywhere in the server. `ActionType.BACKUP_CREATE` is a declared enum member with no implementation behind it. Simultaneously, the live business database **is tracked in git and is currently dirty**:

```
 M server/database/erp.db
 M server/database/erp.db-shm
 M server/database/erp.db-wal
```

A `git checkout`, `git stash`, `git reset --hard` or `git clean` is, today, an unrecoverable data-loss event. See **DR-01 / DR-05 / #1**.

**How to read the classifications.** Every finding is tagged with a severity (P0 → P3) and a *kind*:

| Kind | Meaning |
|---|---|
| **BUG** | Confirmed defect. Reproduced in code and, where stated, in live data. |
| **ARCH** | Architectural risk. Works today; the structure guarantees future breakage. |
| **ACCT** | Accounting risk. The numbers a business owner or tax filing would rely on are wrong or unsupportable. |
| **IMPROVE** | Genuine improvement, not a defect. |
| **PREF** | Subjective preference. Flagged so you can ignore it. |

P0 = can corrupt money, inventory, accounting or historical data, or is a security hole. P1 = wrong numbers or lost work without corruption. P2 = incorrect but bounded. P3 = cosmetic or latent.

# A. EXECUTIVE SUMMARY

| Dimension | Score | One-line justification |
|---|---|---|
| **Architecture** | **4 / 10** | Conventional and legible layering (routes → controllers → models), but no enforced service layer: stock is mutated from 8 near-identical sites, "invoice total" has 5 disagreeing implementations, and `config/database.ts` performs unguarded data surgery on every boot. |
| **Database** | **3 / 10** | Schema is sensible — real foreign keys, good `UNIQUE` constraints, `integrity_check` clean, `foreign_key_check` clean. Undone by: no migration ledger at all (`user_version = 0`, 47 hand-rolled runners), one *already-executed* data-loss migration, money stored as floating point, no CHECK invariants protecting any cached aggregate. |
| **Accounting** | **2 / 10** | A genuinely correct double-entry posting engine exists — and roughly half the business never calls it. Purchases, supplier payments, expenses and POS post nothing. `Cash` has **zero credits in its entire lifetime**; `Accounts Payable`, `Owner's Equity`, `Retained Earnings` and `Operating Expenses` have **never been touched**. Inventory Asset currently reads **−69,553.80**. |
| **Inventory** | **4 / 10** | The best-engineered domain. `stock_movements` is a proper append-only signed ledger; FEFO/FIFO batch consumption is correct; `Production` is a reference-quality implementation. Undermined by physical counts that never touch cost layers, a stock transfer orchestrated by the *client* in two HTTP calls, and boot-time synthesis of cost layers with no journal entry. |
| **Backend** | **5 / 10** | Prepared statements throughout; 59 transaction bodies with **zero** async-in-transaction bugs (a class of error this codebase has entirely avoided); permission middleware on essentially every route. Against that: 52 swallowing `catch` blocks, `strict: false`, no `typecheck` script, 12 exported report handlers with no route. |
| **Frontend** | **5 / 10** | Unusually disciplined presentation layer — **no business total is recomputed client-side anywhere**, sealed `ApiResult`, no optimistic updates, no retry interceptor, secure token storage. But the declared architecture is fiction (see F), the mobile card system is ~12% built, POS does not exist in the client, and two endpoints the client calls have no server handler. |
| **Security** | **3 / 10** | Real foundations: bcrypt cost 12, JWT, an 83-permission RBAC model, IDOR scoping, sort-parameter allowlists, CSV-injection escaping, upload MIME allowlist, and a 379-line security regression test. Then: two SQL injections, a privilege-escalation path to Admin, a committed JWT secret, and `NODE_ENV=development` in the committed `.env` which disables the rate limiters. |
| **Data integrity** | **3 / 10** | Structurally clean at the SQLite level, and there is no negative stock. But every cached aggregate — `paid_amount`, `balance_amount`, `status`, `current_stock`, `stock_balances` — is *rewritten from scratch at every boot* rather than protected, which means the write paths are never actually held to account. Orphaned GL and ledger rows are inside live reports right now. |
| **Performance** | **5 / 10** | Fine at present scale (a 1.1 MB database) and 17 of 18 list endpoints are properly paginated. But `invoice_items` has **zero indexes**, saving one invoice is O(that customer's entire history), and global search issues ~2,000 queries per keystroke. |
| **Auditability** | **2 / 10** | `activity_log` exists, has no UPDATE path (correct), and holds 150 rows. It records no before-value, no after-value and no reason; `deleteInvoice` writes **zero** audit rows; 30 of ~60 declared action types are dead. You cannot answer "who changed this invoice's amount, from what, and why." |
| **Maintainability** | **4 / 10** | Consistent layout, real TypeScript interfaces, and good tests where it matters most (FIFO/batch, purchase returns). Against that: 17 dead report functions each carrying a divergent formula, 11 of 30 rollback files containing invalid SQL, no CI of any kind, and an `AGENTS.md` whose "non-negotiable" architecture invariant is three-quarters false. |

**Overall.** As an *application* this is a competent, feature-rich build with several genuinely well-engineered subsystems — the accounting posting engine, the batch consumption logic, `Production`, `PurchaseReturn`, and the Flutter presentation layer are all work I would keep and copy from. As a *financial system of record* it is not currently trustworthy: the general ledger is decorative, the reports that an owner would act on are internally contradictory, historical documents are hard-deleted without audit, and there is no backup. **Roughly 3.5 / 10 as a book of account; 5 / 10 as software.**

The good news is that the gap is narrower than it looks. The correct patterns already exist inside this codebase — they are just not applied uniformly. Most of Phase 1 in section K is *calling code that is already written* from the ~9 paths that skip it, plus one 10-line fix for the 1 September outage, plus a backup.
